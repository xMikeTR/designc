designc guide

A step-by-step guide for your first hour with designc. You follow it on a sample project, so you need no key, no account and no model. Each step says what to click and what you should see.

1. The idea 2. Start the app 3. The screen 4. Walkthrough 5. The other views 6. Your own folder 7. Agents Terms When you are stuck

1. The idea, in one picture

In designc you write down the design of a system, and designc checks it the way a compiler checks code. It tells you what looks wrong or is unknown, and it keeps a yes/no answer called the gate: is this design ready to build? When the gate says yes, you freeze the design into a handover, and a coding pipeline builds from that.

  you write the design ──► designc checks it ──► findings + gate
          ▲                                        │
          │       you fix the model or record      │
          └──────── a decision for each finding ◄──┘

  gate ready ──► Freeze ──► handover ──► a coding pipeline builds it
                                               │
  Build and Improve views ◄──── ledger ◄───────┘  (what happened, what escaped)

Everything is plain files in one folder (the registry), so git gives you review and history. Agents can explain and draft things, but only you bind a decision or freeze a handover.

2. Start the app

From the source folder (needs Node 20 or later):

npm install
npm start

Or run the installer you were given. The app opens on a welcome page:

  1. Read the six tour steps if you like (Next, or Skip tour). Help → Take the Tour shows it again later.
  2. Click Try the sample project. designc copies a small pricing-engine design to Documents/designc-sample-registry (and its code to Documents/designc-sample-codebase) and opens it. You are working on a copy, so you can change anything.
Start with the sample, not your own folder. The sample already has findings, a decision, a requirement and pipeline history, so every view has something to show. Setting up your own folder is section 6.

4. Walkthrough on the sample

About 20 minutes. Do the steps in order.

4.1 Read the model

  1. Click the Explorer icon, then model → workspace.dsl.
  2. This is the design, written in Structurizr DSL: people, systems and containers, and arrows between them (a -> b "description"). The "d.…" lines under properties are what designc checks, for example "d.instances" "1" (how many copies run) or "d.critical" "yes".
  3. Hover a d. property to see what it means. Typing "d. offers the full list.

4.2 Read the findings

  1. Look at the Problems panel at the bottom. Each line is a finding: a red one is an error, an orange one a warning. The code on the right (for example DC002) is the rule, and [Ln 53] the line.
  2. Click a finding. The editor jumps to that line.
  3. Read one in plain words. "Quotes DB: lost update: 2 containers write "Quote" and at least one has no concurrency control" means two parts of the system write the same data and nothing stops them overwriting each other.

Some warnings say undeclared property. designc asks for a property only where it needs one to decide. That is not an error in the file: it is a question the design has not answered yet.

4.3 Fix one finding by editing the model

  1. In Problems, click Rating Engine: critical, but runs 1 instance. The editor jumps to line 35.
  2. Change "d.instances" "1" to "d.instances" "2".
  3. Press Ctrl+S.

That is the main loop: change the design, save, and see what designc thinks now.

4.4 Look at the gate

  1. Click the Design icon (second from the top).
  2. Under Ready gate is the list of everything still blocking (the status bar shows the count). The first line is marked next: start there.
  3. Each line has its own buttons. For a finding: Record decision, Accept risk, and Ask the tutor (needs an agent, section 7).

4.5 Record a decision

Not every finding is fixed by editing the model. Sometimes the answer is a rule the code must follow, such as "the worker ignores a message it has already processed". You record that as a decision.

  1. On a finding in the gate list, for example DC004 on Cat Model Adapter, click Record decision.
  2. A box asks what was decided. Type one sentence and click OK.

designc writes the decision to decisions/<name>.yaml and opens it:

  1. Fill in rationale (why) and replace the TODO under checks with a real command if you have one. A check is a shell command: exit code 0 means it passed.
  2. Back in the Design view, the gate now has a line for this decision with a Bind button. Binding means "I accept this as part of the design". Only a person can bind; agents can draft but never bind.

Notice the gate went up by one when you recorded the decision. That is expected: a draft decision blocks until someone binds it and its check passes.

4.6 Compare the design with the code

  1. Click the Code map icon (the map), then Extract the as-built map. The sample already points at its codebase.
  2. designc reads the code (it never changes it) and draws what is actually built.

Click a box to see the evidence: which file and line made designc draw it. The difference between the two is called drift.

4.7 What you cannot do on the sample

Freeze (in the Design view) is refused because the gate is not ready. This is on purpose: a handover can only be made from a design with nothing blocking, and only by a person.

5. The other views, briefly

These show what happens after a handover. On the sample they show made-up data marked sample data.

  • Build: runs, cost, failures and questions from the pipeline. A question here (Waiting on a decision) also blocks the gate until you answer it.
  • Work: work items. Start, run the gates, mark Done. Done needs evidence: a passing gate at a commit that is on main.
  • Improve: escapes (defects that got through) and which stage should have caught them, so the rules get better over time.

6. Set up your own folder

Do this once the sample makes sense.

6.1 Create and open the folder

  1. Make an empty folder, for example design/ inside your code repository. Beside it works too.
  2. In designc: File → Open Design Folder… (or Open design folder on the welcome page) and choose it.
  3. designc sees there is no designc.json and opens Set up this folder.

6.2 Fill in the Set up page

SectionWhat to choose the first time
What this folder isDesign registry. (A study notebook is for researching a topic before deciding; a domain pack is for sharing domain rules between teams.)
ModelKeep model/workspace.dsl and tick Create it with a small starter model.
Read-only referencesSkip. Used to point a build at a legacy app it is replacing.
Model provider (LLM)Skip for now, or see 6.3. You need it only for the built-in agent and the Grill-me button.
LangfuseSkip. It is where a pipeline's agent runs are traced; Build reads them from there.

Click Create designc.json. You now have designc.json and a starter model. Open the model and start describing your system; findings appear as you type.

To compare with code later, add "codebase": "../path-to-your-repo" to designc.json (relative to the folder), or use Choose codebase folder on the Code map.

6.3 Keys: where they go

This is the part that trips people up. designc.json never holds a key, only the name of an environment variable, so the file is safe to commit. The key itself must be in the environment before designc starts, because the app reads it from its own process.

  1. In a terminal, from the designc source folder, run scripts/setup-wizard.sh path/to/your/folder. It asks step by step, writes only variable names to designc.json, and saves the keys to ~/.config/designc/env, outside every repo.
  2. Start designc from a terminal that has loaded them: 
    source ~/.config/designc/env && npm start -- path/to/your/folder
  3. The status bar's LLM item should no longer say not configured. If it still does, the key was not in the environment when the app started.

Started from a desktop shortcut or the installer, the app does not see variables set only in a terminal. Either start it from that terminal, or set the variable for your whole session.

6.4 The trust question

The first time you run a check, use git or open the terminal in a folder, designc asks whether you trust it, as VS Code does. Checks are shell commands from the folder's files, so only trust a folder whose contents you know. You can trust just this folder, the repository around it, or the parent folder.

6.5 A first model

If you skipped the starter, this is enough to begin:

workspace "My system" {
  model {
    user = person "User"
    app = softwareSystem "My app" {
      web = container "Web" "" "React"
      api = container "API" "" ".NET 8"
      db  = container "Database" "" "SQL Server" { tags "Database" }
    }
    user -> web "Uses"
    web -> api "Calls" "HTTPS"
    api -> db "Reads and writes"
  }
}

Save it and look at Problems and the C4 sheet. Then go to the Design view and work the gate from the top.

7. Agents (optional)

The speech bubble at the bottom of the activity bar opens the agent panel.

  • Which agent: designc (gateway) uses the model provider from section 6.3. Claude Code (and other ACP agents) uses that tool's own login instead, so if you already use Claude Code you can pick it with no key in designc.
  • Role: Architect (talk about the design), Grill-me (asks you hard questions, one at a time), Tutor (explains, never writes), Analyst (for Improve).
  • An agent can read everything in the folder. When it wants to write, you see a card with the change and Approve or Reject. Nothing is written without that.

Terms

TermMeaning
RegistryThe folder that holds one design. Plain files, kept in git.
ModelThe design file, model/workspace.dsl, in Structurizr DSL with d.* properties.
FindingSomething the checker thinks is wrong or unknown in the design. Rule codes DC000 to DC009.
GateThe yes/no answer to "is this design ready to build?", with the list of what still blocks.
DecisionA recorded answer to a finding or requirement. Minted (drafted) → checked → bound (agreed by a person).
CheckA shell command that proves a decision holds. Exit code 0 is a pass.
Accept riskKeeping a finding on purpose. It must rest on a business decision someone agreed.
RequirementA piece of work from outside, such as a Jira ticket, mapped to the elements it touches.
HandoverA frozen copy of a ready design that a pipeline builds from. Never rewritten.
Code map, driftThe design read back from the code, and where the two differ.
LedgerAppend-only log of what happened (checks, handovers, pipeline runs), in ledger/*.jsonl.
EscapeA defect that got through. Improve records which stage should have caught it.

When you are stuck

What you seeWhat to do
The welcome page and nothing elseNo folder is open. Click Try the sample project.
"LLM: not configured" in the status barExpected until you do 6.3. Everything except the built-in agent and Grill-me works without it.
The gate went up after I did somethingA new draft decision blocks until it is bound. Look at the new line in the gate.
Freeze is refusedThe gate is not ready, a file has unsaved changes, or a gate file is not committed. The message says which.
A check failed with exit code 127The shell could not find the program. Output names it.
Extract says it found no containerPoint codebase at the folder that holds the app, not only a library or test project.
A finding I do not understandAsk the tutor on it, or Help → Design Properties Reference for what each d.* means.

More detail: README.md in the app folder covers every property and rule; AGENTS.md is the technical reference for people changing designc.
