# AGENTS.md: designc desktop

Technical context for coding agents (and people) changing this codebase. Read this before editing. It describes what exists as of version 0.1.0; where the code and this file disagree, the code wins and this file should be fixed in the same change.

## What designc is

designc is an Electron desktop IDE for system design in which the design is the source of truth and code is a build output. It hosts three systems of a design-to-code factory in one window:

| View | System | Purpose |
| --- | --- | --- |
| Design | Design compiler | Structurizr DSL model with `d.*` design properties, live lint (DC000 to DC009), C4 sheet, decisions, requirements, definition-of-ready gate, grill-me, handover |
| Code map | As-built | Deterministic extraction of a .NET and JS/TS codebase into a C4 model with evidence, down to component level, overlaid on the design as drift (`Core.driftModels` for containers, `Core.driftComponents` for components) |
| Build | Coding pipeline | Agent runs from Langfuse plus pipeline events from the ledger: tokens per passing task, reruns, decision check results, needs-decision items, drift |
| Improve | Evals and improvement loop | Escapes by the stage that should have caught them, rule health, proposals, escape suggestions from telemetry |
| Parity | Legacy UI parity | Scenarios replayed on the legacy app and the new one by an outside recorder; baselines, reports, findings and screenshots side by side, read-only. A pass is a work item `done_when` entry |
| Deployment | As designed | Read-only view of one declared deployment view or whole `deploymentEnvironment` (picker; default `designc.json` `deployment`); click a node to see what is lost and what goes down if it is unavailable |
| Agent panel | All | Chat pane with roles (Architect, Grill-me, Analyst, Tutor). Three agent kinds: built-in through an OpenAI-compatible gateway, any Agent Client Protocol (ACP) agent, or a remote AG-UI agent service such as a MAF host |

The governing principle, which every change must preserve: **probabilistic components propose; deterministic components and humans decide.** Agents never write anything without a policy check and, for writes, an explicit human approval.

## Stack and conventions

The app is plain Electron 33 with vanilla JavaScript. There is no framework, no bundler and no TypeScript. Monaco (0.52, AMD build) is loaded from `node_modules/monaco-editor/min/vs`, and js-yaml from its UMD bundle. Keep it that way unless there is a strong reason: the renderer is loaded as classic scripts from `file://` under a strict CSP.

Code style: 2-space indent, single quotes, semicolons, small pure functions, `const` over `let`. Renderer files share one global script scope: `app.js` declares the state object `A` and helpers (`$`, `esc`, `plural`, `trunc`, `hash`, `fmtN`, `when`, `nextId`, `debounce`, `toast`, `yamlList`, `yamlStr`, `readText`, `openFile`, `save`, `recompile`, `renderAll` and others) that `agent.js` uses directly. Do not introduce ES modules into the renderer without converting all three renderer scripts.

Every HTML string built in the renderer must pass user or file content through `esc()`. There is no templating library; `innerHTML` is used throughout, so escaping is the XSS boundary.

`window.prompt` does not work in Electron (it returns nothing); use `askText(message, value)` in `app.js`, which resolves to the text or null on Cancel. UI text follows plain, specific wording: sentence case, no ALL CAPS except VS Code-style sidebar section headers, no exclamation marks. Error messages say what happened and what to do next.

## Running, building, testing

```
npm install
npm start                        # opens the app
npm start -- /path/to/registry   # opens straight into a registry folder
npm run dist:win | dist:mac | dist:linux   # electron-builder installers in dist/
```

Requires Node 20 or later. Installers are unsigned. `npm install` runs `electron-builder install-app-deps` (postinstall), which rebuilds `node-pty` for Electron's ABI; without it the Terminal panel says it could not start and everything else works. A plain-Node `require('node-pty')` fails after that rebuild, so tests use a fake (`test/terminal.test.js`).

Unit tests run with `npm test` (`node --test "test/**/*.test.js"`). Tests are done four ways. Note that mock servers must be started in the same shell command as the app when running under a sandbox that kills background processes between commands.

The four ways, and a change should use whichever applies:

1. **Core logic in Node.** `renderer/core.js`, `extract.js` and `telemetry.js` are plain CommonJS-compatible modules and can be required from Node directly, for example `node -e "const C=require('./renderer/core.js'); ..."`. The compiler core must keep producing the same findings as the Python CLI in `python/designc` (same rule codes, messages and severities; `test/designc-cli.test.js` compares them) on `sample-registry/model/workspace.dsl`: 2 errors (DC002, DC004), 5 warnings (DC001, DC003, DC005, DC006, DC008, two of them `unknown`), 1 suppressed (DC005 on Cat Model Adapter).
2. **End-to-end journeys.** `e2e/journeys.spec.js` drives the app through Playwright's `_electron` (`npm run e2e`; on Linux without a display `xvfb-run -a npm run e2e`). One `@critical` test per main journey: open a registry, see the model's findings, bind a decision, freeze a handover (refused on `sample-registry`, done once on `e2e/fixtures/ready-registry`, refused again as already frozen), extract the code map, track a work item, study a topic and decide from it (`fixtures/study-registry` with the mock ACP agent, then `fixtures/study-project`), pin a domain pack, and see legacy parity on a work card and in the Parity view (`fixtures/parity-registry`; the journey writes its own screenshot because shots are not in git). `launch(reg, {ready})` takes the locator that says the folder has loaded (default the gate; a study notebook has none). `e2e/helpers.js` launches on a scratch copy of the registry, outside git, with a scratch `--user-data-dir` holding `trustAllFolders: true` (never the user's `state.json`), and waits for the status bar's gate before acting. Locators are roles, accessible names and visible text, scoped to a region by id where needed. `scripts/agent-gate.sh` is a Claude Code Stop hook (`.claude/settings.json`): when an app file changed since the last pass it runs the `@critical` journeys and exits 2 on failure, so an agent cannot end its turn on a broken app. **Agents never delete, skip, focus or loosen these tests; fix the app or ask the person.** `test/e2e-guard.test.js` fails on `test.skip`/`only`/`fixme`/`fail` and on a missing journey title. A change to a journey's user-visible behaviour updates the journey in the same change; a new main journey adds a test and its title to the guard.
3. **Headless app runs.** `main.js` has a screenshot harness enabled only by environment variables: `DESIGNC_SNAPSHOT=<prefix>` and `DESIGNC_STEPS='<JSON array of renderer scripts>'`. It waits 4 s after load, runs each script with `executeJavaScript` (logging `[step] <result>`), waits 1.5 s, writes `<prefix>-N.png`, then quits. Renderer console errors are printed as `[renderer] ...`. On Linux: `xvfb-run -a -s "-screen 0 1440x920x24" npx electron . --no-sandbox --disable-gpu /path/to/registry`. Always run against a copy of `sample-registry` (and `sample-codebase` copied as a sibling named `designc-sample-codebase`) because flows write files.
4. **Mocks.** `dev/mock-agui-server.js` is a scripted AG-UI service shaped like a MAF host on port 8790 (set `MOCK_REGISTRY` to let its approved tool write the model, and `EXPECT_AUTH` to require a bearer header). `dev/mock-gateway.js` is a scripted OpenAI-compatible streaming gateway (tool calls included) on port 8765. `dev/mock-acp-agent.js` is a scripted ACP v1 agent that connects to designc's MCP server, sends a plan, asks permission, writes through `fs/write_text_file`, attempts a write outside the registry, and mints a decision over MCP. Set `MOCK_BYPASS=1` in its env to also make it write a file directly on disk and append a forged check to the ledger (both must be flagged as `unapproved_change`), and attempt two ACP writes designc must refuse: a path that leaves the registry through `..`, and a decision with `status: "bound"`.

## Process model

| Process | Files | Responsibilities |
| --- | --- | --- |
| Main | `main.js`, `acp.js`, `extract.js`, `telemetry.js`, `terminal.js` | Owns the file system, scoped to the open folder; file watcher; ledger appends; decision check runs; the integrated terminal's shell; LLM gateway calls; Langfuse reads; codebase extraction and search; ACP agent processes; the MCP bridge HTTP server; menus |
| Preload | `preload.js` | The only bridge. Exposes `window.host` via `contextBridge`. Context isolation on, Node off in the renderer, sandbox on |
| Renderer | `renderer/index.html`, `core.js`, `app.js`, `agent.js`, `styles.css` | All UI and all policy decisions for agents: compiler, views, panels, approvals |
| MCP server | `designc-mcp.js` | Stateless stdio MCP server launched by ACP agents. Forwards `tools/list` and `tools/call` to the main process over 127.0.0.1 with a per-run bearer token; the main process asks the renderer |

Security invariants in the main process: every registry path goes through `inside(rel)`, which calls `confine` in `paths.js`: it rejects anything outside the open folder, lexically and after resolving symlinks. Child processes (check runner, ACP agents) get `childEnv`, the environment minus names that look like secrets (KEY, SECRET, TOKEN, PASSWORD, CREDENTIAL, AUTH); `designc.json` `inheritEnv` (checks) and `acpAgents.<key>.inherit` list names to pass through anyway. Codebase paths go through `codebaseDir(p)` and the `codebase:read` handler rejects escapes. Codebase access is read-only everywhere. `will-navigate` is blocked and external links open in the system browser.

### Ledger envelope v1

`renderer/ledger.js` (dual-loaded like `core.js`: `<script>` in the renderer, `require()` from `ledger-store.js` and tests) owns the schema. Every event has a `designc_v1` envelope: `schema_version: 1`, `event_id`, `ts` (epoch ms), `kind`, `by`, plus the kind's own fields. Two rules make this the one append path: `ledger-store.js` (`appendEvent`) validates against `Ledger.validate`, stamps the envelope, routes by `kind` to its stream file, and appends — it is the only writer; there is no legacy bridge and no code anywhere hand-rolls a `ledger/*.jsonl` line (`test/ledger-guard.test.js` asserts this). `Ledger.order(events)` merges the per-file streams: it drops a repeated `event_id` and stable-sorts by `_ts`, so a union-merged ledger reads the same in any order. Escape ids are minted by `Ledger.escapeId(uuid)` (`E-` plus 8 hex), not counted. `Ledger.parse` upcasts pre-v1 lines that have no `schema_version` (`_legacy: true`, a synthetic `event_id`) so old and new lines read back as one stream; a line carrying an `envelope_version` instead is a `harness_v1` (Build / MAF) event, a disjoint kind set in the same files, not a designc kind.

**Two envelopes.** `harness_v1` is the grill-me / MAF session and charter envelope (`Ledger.HARNESS_KINDS`, 15 PascalCase kinds — `SessionStarted`, `GateFailed`, `NeedsDecision`, `HumanDecision`, etc. — ported as-is from the harness's own `event.py`), routed to `ledger/sessions.jsonl` via `Ledger.validateHarness` and `recordSessionEvent`. It is disjoint from the designc kind set (R-3): a designc kind carrying `envelope_version`, or a harness kind carrying `schema_version`, is rejected. `parse()` dispatches per line on which version key is present and stamps every loaded event with `_ts` (epoch ms; designc keeps its numeric `ts`, harness's ISO `ts` is `Date.parse`d) — `Core.latestCheck` and the Improve escape sort read `_ts`, never the raw `ts`. `Ledger.resolvedEventIds(events)` finds harness `NeedsDecision` events a `HumanDecision.payload.cites_event_id` has answered; the designc `needs_decision` kind is still resolved by `needs_decision_resolved` via `derive()` (which attaches `resolution {by, ts, option, note, decision}`; `Ledger.ndOptions(nd)` gives the pipeline's offered `payload.options` and `recommended`, each shown with a Choose button that records `payload.option` and an optional `payload.note`; Answer with a decision also records the resolution with `decision`) — the gate only ever counts the designc kind (R-4), so an open harness `NeedsDecision` never blocks it.

The ledger is append-only. The app never rewrites a line; state changes are later events that `Ledger.derive()` folds in; an open pipeline `needs_decision` keeps blocking the gate until a person writes `needs_decision_resolved` (`escape_classified` sets an escape's `caught_by`; `needs_decision_resolved` closes a needs-decision).

| `item_done` | `item, commit, evidence[]` — a person declares a work item done after designc checked every `done_when` entry and that `commit` is reachable from main; `designc.jsonl` | App |

Events with `"sample": true` are sample data and the UI labels them. The Improve view reads `agents.jsonl` back: `Ledger.agentActivity(events)` (pure, `test/agent-activity.test.js`) gives one row per agent and role (turns, tokens, tool verdicts, declined writes, permissions, approvals, unapproved changes), shown as "Agent activity" with an "Unapproved changes" list in `improveDash`.

**Factory evals (suite runs).** `Ledger.suiteRuns(events, {k})` (pure, `test/factory-suite-runs.test.js`) derives each suite run from `factory.jsonl`: a trial is `fail` if any pinned gate failed, `pass` if every gate passed, otherwise `incomplete` while the run is open and `harness` once `suite_run_finished` is recorded (a harness failure, not an agent one, left out of pass@1). Gradients never decide; the latest event per grader wins; gate events after the finish are ignored, gradients still count; events naming an undeclared task, trial or grader are counted as `stray`; the first `suite_run` per id and the first finish win. pass@1 is the share of judged trials that passed, pass^k is pass@1 to the power `k` (`designc.json` `factory.k`, default 3), and "every trial passed" is shown beside it; run figures are means over tasks with a judged trial. `Ledger.failureModes(events, {taxonomy, escapes})` (pure, `test/factory-failure-modes.test.js`) counts escapes per mode from `factory/taxonomy.yaml` (`modes: [{id, name, triage?: spec|fix|grader, description?}]`, read by `loadTaxonomy` in `app.js`; not a gate input and not read by the CLI). An id the taxonomy does not list, or a malformed taxonomy, is a warning shown in Improve, never a gate clause. Improve shows "Failure modes" and a classify dropdown per escape in the other-registries table. `Ledger.factoryTasks(events, {tasks, taxonomy, runs})` (pure, `test/factory-tasks.test.js`) gives each `factory/tasks/*.yaml` its status: the file says `minted`, `checked` or `retired`; `bound` is never in a file, it is the latest `factory_task_bound` whose hash matches the file's, and a mismatch is `changed` until re-bound. Binding is refused without `source.failure_mode` (`Ledger.taskBindProblem`; an id the taxonomy lacks is only a warning), refused while the file has unsaved edits, and names suite runs that pinned another hash ("used a different definition"). The Analyst may write `factory/tasks/*.yaml` through ACP (`Policy.WRITE_PATHS`), but `writeVerdict` refuses `status: bound` and `bound_by`/`bound_at`/`hash`; the taxonomy is a human file. Improve shows these as "Eval tasks" with Bind and Re-bind. `Ledger.calibrationStatus(labels, {now, threshold, maxAgeDays})` (pure, `test/factory-calibration.test.js`) judges each `factory/labels/<dimension>.yaml` (human-written, no ledger kind, no agent write path): `rounds: [{date, judge_version, precision, recall, n}]`. The latest valid round by date decides: `below` when precision or recall is under the threshold (0.8, or `designc.json` `factory.calibrationThreshold`), else `stale` when older than 30 days, else `ok`; no valid round is `uncalibrated`; invalid rounds are listed as problems and skipped. It is display only ("Judge calibration" in Improve, `loadLabels` and `calibrationHtml` in `app.js`) and never reaches the gate. `fixtures/factory-registry/factory/labels/` holds two dimensions. The wire contract for the harness is `docs/factory-evals-contract.md`. Improve also shows "Escapes in other registries" (`loadRegistries`, `otherRegistriesHtml` in `app.js`): the escapes in each registry listed in `designc.json` `registries`, with their stage, read-only, with Refresh; a missing folder or unreadable ledger line is named, not fatal. Improve shows suite runs as "Suite runs" (`suiteRunsHtml` in `app.js`), newest first, a run expanding to per-task trial chips (hover for each grader's verdict; a chip links to the Langfuse trace when `langfuse.baseUrl` and a project id are known). The section appears only when there are suite runs. `Ledger.suiteCompare(runs)` (pure, `test/factory-suite-compare.test.js`) compares each run with its baseline, the latest earlier run of the same suite on a different `harness_version` that has a score; a run on an already-run version is a repeat (`repeatOf`) and never its own version's baseline. Only eval tasks whose hash matches the baseline and that are judged on both sides are compared (status `compared`; otherwise `changed`, `new` or `unscored`, plus `dropped` for baseline tasks missing from the run), and the run's change is the mean of those task deltas. Improve shows one table per suite with a Change column (percentage points of pass@1 and pass^k, a repeat tag) and the per-task change when a run is expanded. Eval tasks are named `task_id` and the kinds carry no `task` field, so they never mix with the pipeline's `task` kind.

## The design compiler (`renderer/core.js`)

`Core.parse(src)` tokenizes and parses a Structurizr DSL subset: `workspace`, `model`, `person`, `softwareSystem`, `container`, `component`, identifiers with `=`, `properties`, `tags`, `description`, `technology`, relationships `a -> b "desc" "tech" { properties {...} }` including implicit-source `-> b` inside element bodies. Unknown blocks such as `views` are skipped. It returns a model with `elements` (Map), `rels`, `errors` (with 1-based lines), and helpers `label`, `isAncestor`, `locEl`, `locRel`.

`Core.check(model, {chainHops})` runs `validate` (DC000: unknown `d.*` keys with did-you-mean, malformed values), then every rule in `RULES`, then applies `d.suppress` suppressions. Diagnostics have `{code, sev, msg, loc: {kind, id, label, names, line}, hint, unknown, suppressed, related[]}`.

Properties are **demand-driven**: nothing is globally required. A rule emits an `unknown` warning only where it needs an undeclared property to decide. Keep new rules this way.

`Core.gate({model, diags, decisions, requirements, ledger})` returns `{ready, clauses[]}`. Blocking clauses: parse errors; unsuppressed findings not covered by a bound `accept` decision that binds the element and resolves the code; decisions not bound; bound decisions without checks or without a passing latest check (a technical `accept` whose `checks` are empty or only `TODO` placeholders needs none: it rests on its business decision); `fix` decisions whose finding still fires; untraced requirements; open needs-decisions; a repeated decision or requirement id (`duplicate id <id>`); any registry file that does not parse (`<path> does not parse`, from the optional `registryErrors` input, fed by `A.yamlErrors`). A repeated proposal id is shown in Problems, not in the gate. The Design sidebar (`designSidebar`, `gateOrder`, `clauseActions` in `app.js`) lists the clauses in working order (parse, registry, duplicate, finding, decision, evidence, check, promotion, assumption, requirement, scenario, eval, needs), marks the first `next`, and gives each kind its own button: a finding gets Record decision, Accept risk and Ask the tutor (or a link to the decision that already answers it, from `Core.decisionsFor`), an unbound decision Bind, a promotion clause Re-bind, a check Run check, an overdue assumption Mark reviewed, an eval Run eval, a needs-decision Answer with a decision (`answerNeedsDecision`: asks for the statement, then the command that proves it (`askCheck`: a description is asked again, blank leaves a TODO), binds the element by name though the pipeline names it by elements.json id) and Mark resolved (for a question that is not about the design), a disallowed evidence host Allow <host> (`allowEvidenceHost`: human only, after a confirmation, adds the host to `designc.json` `evidenceHosts`), a business decision without evidence Add evidence (`addEvidence`: human only, asks for an https link, writes `evidence`, then offers to allow its host) and I'm the business (`becomeBusinessOwner`), and an accepted risk without a bound business decision Choose business decision (`chooseBusinessDecision`: human only, picks a business decision or drafts one, and adds it to `relies_on`). `clauseHelp` adds a line under those two clauses saying what to do.

`Core.decisionsFor(finding, decisions)` lists the live (not superseded) decisions that resolve the finding's code and bind one of its elements, bound first. It is display only: Problems shows the first one as a link saying what it waits for (`decisionNote` in `app.js`: bind it, or the model still has to change) in place of Record decision and Accept risk, so a finding with an answer does not invite a second one. `test/decisions-for.test.js`.

`Core.slugId(statement, taken)` makes decision and proposal ids from what they say (kebab-case, at most 48 characters, `-2`, `-3` on a clash) so two branches minting at once do not both take the next number. `nextId` remains for handovers only.

**Handover folder.** `Core.handoverPlan({date, now, by, model, requirements, decisions, behaviour, vocabulary, evals, scenarios, forecast})` is pure and returns `{id, files[]}`. The id is `<yyyymmdd>-<hash8>`; the hash covers the copied content only. Freeze writes `handovers/<id>/handover.yaml` (id, revision `r-<hash8 of the model>`, created, by, model path, requirement, decision and scenario ids, eval hashes, a path and hash per copied file) plus verbatim copies of the model, requirements, bound decisions, `evals/*.yaml`, `scenarios/*.yaml` (so the build receives the quality attribute scenarios and their fitness functions, `TODO` ones included, as what done means), `behaviour/*.p` and `vocabulary/*.yaml` if present, and `elements.json`: `Core.handoverElements(modelText, behaviour)`, the model resolved for whatever coding agent takes the handover (every element by hierarchical id `System/Container/Component`, `d.code` as normalised path patterns and `d.risk` where declared, relationships by id one per pair, `events` announced in behaviour). It is named in `handover.yaml` (`elements:`) and listed with its hash, but derived, so it is not in the id hash. `BUILD.md` (`buildBrief` in `core.js`, `build:` in `handover.yaml`) is derived the same way: the brief any coding agent reads, naming no pipeline, time or person. It lists the build targets (for a whole handover, `focus`: the elements the requirements and bound decisions name, passed in by `freezeHandover`, as "Build these", every other code area as "Context"; with no focus, every code area as one you may write; for an item handover the in-scope ones), the rules (write only in those areas, never the reserved acceptance path, do not change the design), the decision files and what done means (specs, checks, fitness, evals, merged to main), and points at `docs/pipeline-contract.md` for optional ledger writes; a model that does not parse or a `d.code` that is not a path pattern throws (`handover refused: ...`) before anything is written. Its contract is `docs/handover-elements.schema.json` (`designc.handover.elements/1`) with `docs/handover-elements.example.json` pinned to real output in `test/handover-elements.test.js`; designc owns it and consumers conform, so a change of meaning needs a new schema id. A frozen handover is never rewritten: `freezeHandover` refuses when `Core.frozenAs(id, handovers)` finds the same id, or the newest handover with the same content hash ("already frozen as <id>", with Open handover), ignores a second click while a freeze is writing, and `fs:write` creates files under `handovers/` with flag `wx`, so neither a re-freeze nor an editor save can overwrite one. It also refuses while the gate is not ready, any buffer is dirty, or (in a git repository, after asking for folder trust) a gate input has uncommitted changes (`Core.dirtyInputs` over `Core.GATE_INPUTS` plus the model path; `ledger/` is never one), so a handover always names a commit; outside git it records `commit: null`. It records a `gate` event (`recordGate`, skipped when unchanged), then appends a `handover` event with `commit` and `dirty`, then (in a trusted git repo) stages `handovers/<id>` and pre-fills the commit message in Source control for the human to review and commit. `loadRegistry` reads folder handovers beside the older flat `handovers/*.yaml`, ordered by `created`. Agents cannot write under `handovers/` (no role lists it in `WRITE_PATHS`). Extraction needs no skip: it reads source extensions only and a handover holds `.dsl`, `.yaml`, `.json` and `.p`.

**Design tokens and UX rules (slice 34).** `design-tokens/tokens.json` is copied into every handover (`tokens:` in `handover.yaml`, in the id hash). `Core.tokenClauses(text, minTextSize)` (mirrored by `token_clauses` in `gate.py`) judges it as gate clauses of kind `tokens`: a file that does not parse, or a text size token (a path with a `font`/`size`, `fontSize` or `textSize` segment) that is not px or rem or is below the minimum (`designc.json` `ux.minTextSize`, default 12 px; rem is 16 px). Other tokens are not judged and a missing file is not a clause. A criterion may carry `ux: {keyboard?, focus_order?[], focus_return?, breakpoints?[]}`; `acceptanceClauses` checks the types, that locator names are declared and widths are whole pixels from 200 to 4000. `acceptanceSpecs` then adds axe, keyboard, focus order, focus return and per-breakpoint no-horizontal-scroll tests (only what `ux` declares). The Design sidebar has a Design tokens section (New file). Stylelint and the axe run are the pipeline's gates, not designc's. Tests: `test/ux-tokens.test.js`.

**Acceptance criteria (slice 27).** `acceptance/*.yaml` is a gate input (dirty inputs, `GATE_INPUTS`, `record.py`). `Core.acceptanceClauses({model, acceptance, requirements, decisions})`, called by `Core.gate` through its `acceptance` input and mirrored in `python/designc/gate.py` (`acceptance_clauses`, `resolve_element`; `test/acceptance-parity.test.js`), gives clauses of kind `acceptance` carrying `about` (the element name): a malformed criterion, an unknown requirement, decision, element or state, a case without `given` and `then`, no case for a required state, and a requirement element tagged `UI` with no criterion. The required states are `ready`, `loading`, `empty` and `error`, plus `forbidden` where a relationship with `d.authenticated "yes"` points into the element or a descendant, or the criterion lists it in `states`. UI-facing means the element carries the `UI` tag. Because the clauses carry `about`, `Core.scopedGate` already makes a work item unable to freeze without a criterion for each UI element in scope. A handover copies the criteria it touches (an item handover: those of its requirement on in-scope elements) under `acceptance/` and lists their ids as `acceptance:` in `handover.yaml`; the key is written only when there are any. The Design sidebar has an Acceptance section with New criterion (`newAcceptance`); the gate clause's button opens it. Locator contract (slice 29, same function, same Python mirror): a case may list `uses: [names]`; each must be declared in `locators` (`{role, name}`), the role must be in `LOCATOR_ROLES` (ARIA roles plus `label`, for `getByLabel`), and a locator needs an accessible name. It is a gate clause, not a DC rule. Spec skeletons (slice 30): `Core.acceptanceSpecs({model, criteria, inScope})` is pure and writes one deterministic Playwright spec per criterion to `tests/acceptance/<element-slug>/<id>.spec.ts` in the handover (header "GENERATED ... Do not edit", `getByRole`/`getByLabel` only, given/when/then as comments). They are derived, so listed and hashed in `handover.yaml` (`specs:`, and `loop_specs:` for an item: the in-scope elements' specs plus those of everything that depends on them by `blastRadius`) but outside the id; the full suite runs at merge. Shared fixture: when there are specs, `tests/acceptance/fixture.ts` (`acceptanceFixture` in `core-handover.js`, derived, listed and hashed like a spec, outside the id and the loop) is generated beside them and every spec imports `test` from it, so any spec also fails on a browser console error, an uncaught page error, a failed API call (4xx, 5xx or a network failure) or a serious or critical axe-core violation. The Acceptance section checks that the codebase has the two packages the fixture imports and installs them after a confirmation (`testdeps.js`). `designc.json` `ux.consoleAllow` (regex sources) lists known console noise; it is written into the file, so a change needs a new freeze. Reserved path (slice 31): DC009 also reports a `d.code` that may overlap `tests/acceptance/**` (JS and Python), and an item handover's `elements.json` (/2) names it in `reserved`. Drift flags an extracted SPA whose design match is not tagged `UI` (`uiUntagged` in `Core.driftModels`).

**Domain packs (slice 38).** `Core.gate({domains: {listed, packs, sources, behaviour}})` appends `Domain.clauses` (kind `domain`, carrying `pack` or `about`) only when packs are listed or copied, and returns `notes` (unknowns such as an unreadable source registry, shown as "unknown:" lines in the Domain section and by the CLI, never blocking). `GATE_INPUTS` includes `domain`. `Core.handoverPlan({domain: [{key, text}]})` copies the packs that define an aggregate owned by a touched element (item scope, else the focus, else every owner) to `domain/<key>.yaml` inside the id hash, and writes derived `domain.json` (`designc.handover.domain/1`, `docs/handover-domain.schema.json`, example pinned in `test/handover-domain.test.js`) listed in `handover.yaml` as `domain:` and outside the id; `elements.json` and its schemas are unchanged and BUILD.md gains one rule when present. `pinDomain`/`loadDomains`/`domainBody` in `app.js`; Setup kind `domain` hides the design activities (`kind-domain`).

**Scoped gate and item handover (slice 24).** Gate clauses carry `about` (the element names they concern). `Core.scopedGate(gate, {model, elements, requirement, decisions})` keeps parse, registry and duplicate clauses, the item's requirement clause, decisions binding an in-scope element, and any clause whose `about` touches scope (clauses that name nothing are kept); the rest are counted as `outside`. `freezeHandover(item)` freezes against that gate: the whole model and `elements.json` (schema `designc.handover.elements/2`, an `in_scope` flag per element; `docs/handover-elements-2.schema.json`, `docs/handover-elements-2.example.json`, pinned in `test/scoped-gate.test.js`) but only the item's requirement and the decisions, scenarios and evals touching scope. `handoverPlan({item: {id, requirement, elements}})` adds `work_item`, `design_version` (the `r-` revision) and `in_scope` to `handover.yaml`, and the id hash also covers the work item id. An item freeze records no `gate` event and no forecast, and its `handover` event carries `item`. `designc check <registry> --item <id>` prints the scoped gate (records nothing; exit 2 for an unknown item); `python/designc/gate.py` `scoped_gate` mirrors it, `test/scoped-gate-parity.test.js` compares the two.

**Re-check (slice 25).** `Core.workRecheck({item, frozen: {model, inScope, requirement}, model, decisions, requirements})` is pure and says whether the design moved under a frozen item: `{stale, reasons[{kind, text}]}` with `scope` (the item's elements or requirement edited since the freeze), `element` (an in-scope element added, removed or changed by fingerprint), `decision` (a bound decision on one, via `changeImpact`) and `finding` (introduced on one). Nothing outside the item's elements counts. The Work view (`refreshRecheck`, `recheckHtml` in `workview.js`) parses the model copy in the item's handover, shows the reasons on the card beside Freeze again, and records `item_recheck` only when the answer for that handover differs from the last recorded one. JS only: the Python CLI has no re-check and the gate never reads it.

**Decision checks.** A check is a shell command run in the registry folder (`runChecks` in `app.js`, through `host.runCheck` after folder trust); exit 0 is a pass, recorded as a `check` event. A check `Policy.checkProblem` rejects (a description such as `Model: ...`) is not run and records nothing: Output says why and a toast counts them, so the gate keeps saying no result rather than a failure that says nothing about the decision. Exit 127 adds a hint naming the program the shell could not find. Agents are told the same rule (`COMMON_RULES`, `ACP_RULES`, the Grill-me instructions) and their decision writes are refused when a check is prose.

**Build decisions.** `effect: build` with `work: <item id>` acknowledges a finding the code has to answer. `Core.gate({workStates})` (`{itemId: backlog|active|done}`, from `Work.states`; `designc check` feeds `work.states`) lets a *bound* build decision cover its finding while the item is backlog or active, so the finding stops blocking but stays in Problems, shown by `decisionNote` as "Building in <item>". It needs no check (like accept). Clauses: a build decision with no `work`, or naming an item that does not exist, and, once the item is done, `<id> says <code> is built, but the model still raises it` with the finding blocking again: the item's `item_done` (human only, with evidence) ends the cover, an agent's claim never does. Problems has Build it beside Accept risk (`buildIt` in `app.js`, human only): pick an open work item or create one from the finding, then write the minted decision; a person still binds it. Agents' `mint_decision` offers fix and accept only. Mirrored in `gate.py` (`work_states`); `test/build-decision.test.js`.

**Business decisions.** A decision carries `kind: business | technical` (absent means technical; anything else blocks). A business decision binds a requirement (`requirement: <id>`), needs no check, and is promoted against that requirement's `version` (`promoted_against: [{requirement, version}]`); bumping the version blocks it as `changed since promotion`. Binding one whose `requirement` is missing or unknown (an Accept risk draft has `requirement: null`) first asks for it (`chooseRequirement` in `app.js`): an existing requirement, or a new `requirements/<id>.yaml` titled from the statement, then writes `requirement` into the decision. `evidence` is mandatory: an https URL whose host is listed in `designc.json` `evidenceHosts` (no list means no host is allowed), unless the decision was bound (`promoted_by`) by someone listed in `designc.json` `businessOwners`: when the person binding is the business, the bind and its `decision_promoted` event are the record (`Core.gate` `businessOwners`, `gate.py` `business_owners`). Evidence an owner does give is still judged. "I'm the business" on the evidence clause (`becomeBusinessOwner` in `app.js`, human only, after a confirmation) adds the app user to `businessOwners`; it is a settings change, so at work it shows in review. `agreed_by` is optional and human-written. A technical decision with `effect: accept` must list a bound business decision in `relies_on`, else the gate says `<id> accepts a risk without a bound business decision`. "Accept risk" on a finding in Problems (`acceptRisk` in `app.js`, human only) asks why, then lets the person pick a business decision or draft one (`PROPOSED:`, empty `evidence`), and writes `accept-<code>-<element>` with `relies_on` and no placeholder check; it binds nothing. `askChoice(message, options)` beside `askText` is the picker it uses. Agents may draft business decisions (`mint_decision` with `kind: business`, statement prefixed `PROPOSED:`; grill-me's "Draft business decision" does the same) but `Policy.writeVerdict` refuses any agent write carrying `evidence` or `agreed_by`.

`Core.blastRadius(model, elementId, {mode: 'misbehaves'})` returns `{down[], degraded[], unknown[], paths[]}` (`{id, name}` entries; `paths` is `{to, kind, via[]}`, one shortest route per affected element). It walks relationships backwards from the element, ignoring ancestor/descendant pairs: a sync caller goes `down` and the damage continues through it; an async caller is `degraded` and stops; a caller with no `d.interaction` is `unknown` and stops (nothing is guessed). An element reached several ways keeps the worst class. Any other mode returns `{error}`. The C4 sheet's badge selector has "Badges: blast radius": select a box and the affected boxes show `down`, `deg` or `?`.

`Core.changeImpact(before, after, {decisions, requirements, chainHops})` says what a model change touches: `decisions` (bound or checked, whose bound element or an incident rel changed, was added or was removed, by fingerprint), `requirements` (those tied to an affected decision or listing a touched element), `introduced` and `resolved` findings (keyed by code and element, suppressed and notes ignored) and a `changed` count from `diffModels`. The Compare tab shows it under the semantic summary for `.dsl` files.

`Core.fingerprint(model, elementId)` returns `{hash, content}` for one element: kind, parent, name, technology, every `d.*` (including `d.suppress`) and every incident rel (direction, other end, technology, its `d.*`). Description, tags, comments, whitespace, order, lines, descendants and rel descriptions are left out. The hash is two FNV-1a 32-bit passes as 16 hex digits, and mirrored in `python/designc/rules.py` (over UTF-16 code units, so it matches for any name). `bindDecision` (human only) writes `promoted_against: [{element, name, hash}]` beside `promoted_by` and `promoted_at`, and appends a `decision_promoted` ledger event. `Core.gate` adds clauses `<id> is bound without a fingerprint`, `<id>: <name> changed since promotion` and `<id>: binding <name> does not resolve` (an entry resolves by its recorded identifier, then by name). `Policy.writeVerdict` refuses agent writes to a decision that carries any of the three promotion fields. Decisions bound before this slice have no fingerprint and block until a human re-binds them: `Core.rebindable(gate)` lists the decisions blocked by a `promotion` clause, the decisions list shows Re-bind on each, and the gate shows one "Re-bind N decisions" button (`rebindAll`, one confirmation, human only, same `bindDecision` path). Re-binding records the current state as accepted, so look at the Compare tab first when the design changed.

`Core.latestHandoverModel(handovers)` returns `{id, path}` of the model copy in the newest handover. The Explorer shows "Compare with last handover" on the model file and opens it in the Compare tab, so a folder that is not a git repository can still see what changed since the last freeze.

`Core.diffModels(before, after)` compares two parsed models by meaning and returns `{elements[], rels[], summary}`. Identity: same DSL identifier is the same element (a name change is a rename, a parent change a move); otherwise same normalised name under the same matched parent; otherwise removed plus added. No fuzzy matching and `d.aka` plays no part. Rels are keyed on matched ends plus their ordinal among parallel rels. It diffs `name`, `kind`, `technology`, `parent` (by name) and every `d.*` key; description, tags, order, whitespace and lines never count. The Compare tab calls it through `semanticDiffHtml` in `gitview.js` for `.dsl` files and says so when either side has parse errors.

`Core.driftModels(design, asbuilt)` matches elements by normalised name (lowercase alphanumerics) or `d.aka`, and returns `toDesign`, `toBuilt`, `relStatus` (matched, undeclared, unmapped), `undeclared`, `unrealised`, `unknownEls`, `missingEls` and `uiUntagged` (extracted single-page apps whose design match is not tagged `UI`, shown in Drift; `test/drift.test.js`).

`Core.atLevel(model, level)` folds every element deeper than `context`, `container` or `component` into its nearest ancestor at that level, lifting rels (explicit rels beat lifted ones, self-loops drop, ids preserved). `Core.containerLevelText(text)` removes component declarations and any rel touching a component from raw DSL text, leaving every other line byte-identical; it relies on the one-line forms `dsl.js` writes.

`Core.view(model, {level, scope})` projects a model for the Code map: `context` and `container` are `atLevel`; `component` keeps everything, or, with `scope` set to a container id, that container's components plus its neighbours folded to container level. Rollup rels covered by visible component rels are dropped; rel ids are preserved.

**Code areas (`d.code`, `d.risk`).** `d.code` lists repo-relative path patterns where an element's code lives; it reaches a coding agent through the handover's `elements.json`, and each file belongs to one element. DC000 reports a pattern `PathPattern.create` rejects, an empty list, a blank entry, and `d.code` without `d.risk` (the handover gives both or neither). DC009 (error, source: the handover contract) reports `d.code` on an element inside one that also declares it (on the inner element, every declaring ancestor in `related`) and two unrelated elements whose patterns `PathPattern.mayOverlap` (once per pair, on the element declared later, the other in `related`; `d.suppress` works). Both are mirrored in `python/designc/rules.py`. `Core.codeAreaDrift(model, files)` judges the areas against `facts.files` (every repo-relative file the walk listed, any type, sorted): `{areas: [{id, name, pattern, matched, hint?}], unclaimed[], files}` (count); `hint` is set when an exact path matches nothing but files sit under it as a folder (an exact path matches one file), or null with no file list. It is display only (the Code map's "Code areas" section, `codeAreasSection` in `app.js`, and `get_code_map`); the codebase is not a gate input, so it never reaches Problems, the gate or the CLI.

`Core.driftComponents(design, built)` judges components only inside a container whose design declares components (*scored*). Components elsewhere are *neutral*, so a container-only design never shows component warnings. It also returns `adoptable` (built containers with components whose design match has none). Rel status adds `neutral` to matched, undeclared and unmapped; cross-container component rels also match the lifted container-level design rel.

`Core.spliceComponents(designText, design, designId, built, builtId)` returns `{text}` or `{error}`. It inserts one built container's components and the rels between them into the design container's block (adding a block if there is none), changing no other line. It refuses if the design container already has components or its block cannot be located. The Code map's "Adopt these components" button calls it, and refuses while the design buffer has unsaved edits. Both it and `suggestCodeAreas` edit text through `insertInBlock(text, el, body)` (lines at the end of an element's block, a block added when there is none; only the declaration line may change).

`Core.suggestCodeAreas(designText)` returns `{text, areas: [{name, pattern, risk}]}` or `{error}`: for a model where no element declares `d.code` (a new project), one area per container, `<system-slug>/<container-slug>/**` (`-2` on a clash) with `d.risk "medium"`, each as its own `properties` block. It refuses a model that does not parse, has no container, or already declares `d.code`, and any result that would not re-parse with exactly those areas. The Design sidebar shows "Suggest code areas" (`codeAreasButton`, `suggestCodeAreas` in `app.js`; human only, refuses while the model buffer is dirty, confirms the list and how many bound decisions will need Re-bind). `test/suggest-code-areas.test.js`.

## Code map extraction (`extract/`)

Deterministic, pattern-based. `extract/index.js` owns the repo walk (SKIP set, file extension filter) and the scanner seam: it builds a shared `ctx = { repo, files, rel, read, opts }`, runs every registered scanner's `scan(ctx)` (`extract/csharp.js`, real; `extract/js.js`, real for package discovery and inbound HTTP routes, delegating outbound calls to `extract/js-calls.js`, also real), merges their Facts (`projects`, `elements`, `edges`, `consumes`, `provides`, `unresolved`), calls `extract/link.js` (passing `opts` through) to match `consumes` against `provides` into edges across languages — including `designc.json` bindings for env-only consumes — and renders the result via `extract/dsl.js`. `opts` comes from `main.js`'s `codebase:extract` handler as `readSettings().extract || {}`, so a `designc.json` with an `extract.bindings` object supplies bindings. ## Agent panel (`renderer/agent.js`)

### Roles and policy

`ROLES` defines `architect` (Design), `grill` (Design), `analyst` (Improve) and `tutor` (Design, read-only: `ask` is empty and `WRITE_PATHS` has no entry, so it can neither call a write tool nor write through ACP), each with `allow` (reads), `ask` (writes needing approval), `instructions` and starter prompts. `roleCfg(role)` merges overrides from `designc.json` `agents`. `verdict(role, tool)` (rules in `Policy.verdict`) **fails closed**: `deny` wins, then `ask`, then `allow`, and anything unlisted is `deny`. A write tool (`Policy.WRITE_TOOLS`) listed under `allow` in `designc.json` still returns `ask`: settings can deny a write tool, never make it silent. Tools not permitted for a role are not even offered to the model (`toolSpecs`), and are still refused if called.

**Researcher (step 0, study).** Offered only in a study registry (`roleFitsKind` hides it elsewhere and hides the others there) and only on ACP or AG-UI agents: on the built-in agent it says `NEEDS_WEB` and offers the agent `webAgent()` picks (the first ACP agent this folder's `designc.json` names, else the first preset). Reads with `read_study`; writes with `add_source`, `add_finding` and `answer_question` (`studyWriter`: validated by `Study` first, then an approval card; `apply` marks the topic in `AG.approved`). `study/` is not in `WRITE_PATHS`, so a raw ACP write there is refused, and opinion and status have no tool. `askResearcher(topic)` opens the panel on that topic. `dev/mock-acp-agent.js` with `MOCK_SCRIPT=study` plays it.

**Tutor.** Teaches system design while the user designs: explains in plain words, ties the answer to the model, names sources (searches the web itself over ACP when the agent can), and ends with one question. `askTutor(question)` in `agent.js` switches to the Tutor, opens the panel and sends the question; it is called from "Ask the tutor" on each model finding in Problems, and from the canvas Inspector through the optional `host.onAsk(question)` hook (the selected element or relationship, the design as a whole, each finding, and the `?` beside each property). The canvas shows none of these buttons when the host gives no `onAsk`.

**Grill-me, "I don't know".** Grill-me's instructions handle an answer of "I don't know": a technical question is researched (`RESEARCH_RULE` in `agent.js`, shared with the Tutor: web search, else web fetch of known pages where search is blocked, else unsourced and said so; never an invented link) and answered with two or three options, sources and a recommendation, and the user chooses; the minted decision is the user's, its rationale saying "Chosen by the user.", "Suggested by Grill-me: ..." and, only when the user gave reasons, "User's view: ...". A business question is never answered by research: Grill-me says who should answer and offers a `PROPOSED:` business decision. The panel shows an I don't know reply under Grill-me's last message, and each sidebar Grill-me question has I don't know (`dontKnow` in `agent.js`, which prefers an ACP agent through `grillInPanel` because the built-in agent cannot search).

**Grill-me without a model.** The Design sidebar's Grill-me (`grill()` in `app.js`) calls `host.chat` when `llm` is set. Without it, `grillInPanel(text)` in `agent.js` switches the panel to the Grill-me role on the chosen ACP or AG-UI agent (or the first ACP agent when the built-in one is chosen), opens it and sends the interrogation prompt. The questions then come one at a time in the panel, and decisions are minted only through the role's approved write path, never bound.

### Tools

Readers (`READERS`): `read_model`, `get_findings`, `get_gate`, `list_decisions`, `read_registry_file`, `get_code_map`, `search_codebase`, `read_code`, `get_telemetry`, for the Analyst only `list_reviews` (the latest failed reviews and the taxonomy modes), for the Researcher only `read_study` (the topics, or one by `id`), for Grill-me only `read_parity` (per scenario its steps, problems, whether a baseline exists, the latest ledger result and the report's findings; never page data or screenshots) and `read_import_page` (one imported page, by requirement id, from the import folder chosen this session in `A.importDir`; each read is an `agent_tool` event). ### AG-UI agents

`sendAgui(text)` keeps a per-chat thread `{threadId, messages, state, resolved, executed}` and runs up to 12 AG-UI runs per user message. Each run POSTs `{threadId, runId, messages, tools, context, state, forwardedProps}`: `tools` are designc's role-filtered tools as frontend tools, `state` is the agent's last state merged with `designcState()` (model revision, findings, gate, drift, decisions), `context` carries the rules and role instructions plus `contextNote()`. A resume run sends `messages: []` and `resume: [...]`.

Events handled: `TEXT_MESSAGE_START/CONTENT/END/CHUNK`, `TOOL_CALL_START/ARGS/END/RESULT`, `STATE_SNAPSHOT`, `STATE_DELTA` (JSON Patch via `applyPatch`), `MESSAGES_SNAPSHOT`, `STEP_STARTED`, `RUN_ERROR`, `RUN_FINISHED`, and any `*THINKING*`/`*REASONING*` event with a `delta`. After a run finishes: unresolved interrupts become approval cards (option ids `accept`/`reject`) and the next run resumes them, each interrupt id at most once (`resolved`); otherwise frontend tool calls without a `TOOL_CALL_RESULT` are executed through `runTool`, each call id at most once (`executed`), and the results are appended as `tool` messages; otherwise the turn ends. An approval sets a 30-second grace window (`AG.graceUntil`) in which registry writes by the host are not flagged.

`agentSawChange(paths)` (called from the file watcher) flags any registry file that changes during an ACP turn without a recent approval in `AG.approved`, shows it in the panel and records `unapproved_change`. Ledger files are included: a change to `ledger/*.jsonl` is flagged unless the app itself appended to that file in the last 8 seconds (`OWN_APPENDS` in `app.js`), so a pipeline appending during an agent turn is flagged too. designc governs what flows through ACP and its own MCP tools; it does not sandbox the agent process.

### Components (`facts.components`, `facts.componentEdges`)

`extract/components.js` assigns each source unit, per owner container, to exactly one component. Precedence:

1. `designc.json` `extract.components` overrides, first matching entry wins.
2. C# anchors: a class with a `[Function]` method, a controller (name ends in `Controller` or derives from `ControllerBase`/`Controller`), or a static class calling `Map*`. Named after the class.
3. C# output-binding types (the `T` a `[Function]` method returns) join that function class's component, even if the class was overridden.
4. A library project or package is one component inside each owner container.
5. Files directly in the project root are `App shell`.
6. JS/TS support folders (`types`, `constants`, `styles`, `assets`, `test`, `tests`, `mocks`, `__mocks__`) are `Shared`.
7. A grouping folder (`features`, `modules`, `domains`) first steps down one level.
8. Otherwise the first folder names the component. F# uses rules 4, 5 and 8 only.

Overrides look like `"extract": { "components": [ { "name": "Ordering", "paths": ["api/src/Shop.Api/Endpoints/**"] } ] }`. A file matched in several containers becomes that component in each. A bad entry, or a glob that matches no source file, goes to `unresolved` (where `designc.json`).

`facts.components` is `{id, key, container, name, owner, basis, tech, files, evidence}`; `facts.componentEdges` is `{from, to, kind, label, tech, via, evidence}` with `via` one of `container-edge`, `queue-internal`, `type`, `di`, `di-candidate`, `import`. Rollup invariant: folding every component edge end to its container and dropping self-loops gives exactly the `(from, to, kind)` set of `facts.edges`, which keeps its container-level shape. The DSL nests components inside their container; container-level rels render as before, and each component rel is one line (`a -> b "label" "tech" { properties { "d.interaction" "sync" } }`) so `Core.containerLevelText` can strip them.

Limits: only service-registration extension methods (`this IServiceCollection` and similar host builders) make a component edge, other extension calls make none; duplicate type names in different namespaces are not resolved; a type name resolves only if exactly one declaration in the deployable's closure has it (otherwise no edge); an interface with several registrations gives `Uses (DI candidate)` edges from the registration root, and the container's unresolved entry lists them once. `test/extract-invariants.test.js` runs the extract-* governance checks (no app-specific names, built-in requires only) in the gate.

### Code level (C4 level 4)

The Code map's fourth level, Code, shows the types of one component (double-click a component, or the Code button) and the types they refer to in other components (dashed, named by component). Selecting a type lists its methods, worst complexity first, with lines, files and what it depends on and is used by. Types and methods live only in `facts.code`, never in the DSL, so drift, lint, fingerprints and the Python CLI are unaffected. It needs a re-extract on a registry extracted before this slice. C# only so far.

**Coverage.** `designc.json` `extract.coverage` lists repo-relative globs of Cobertura (coverlet `coverage.cobertura.xml`) or lcov files, for example `["**/coverage.cobertura.xml", "coverage/lcov.info"]`. Extraction reads them (the normal walk skips `TestResults` and `coverage`, so this has its own walk, skipping only `node_modules` and `.git`), fills `method.coverage` and records `code.coverage {reports, methods, covered}`. Coverage is as fresh as the last extraction. An unreadable or unrecognised report goes to `unresolved` with `where: designc.json`. The type panel shows `cov` and `CRAP` per method.

**Code quality (QC rules).** `designc.json` `quality` maps a metric id to a limit: `{"cyclomatic": 10, "crap": 30, "methodLines": 60, "coupling": 8, "typeMethods": 20}`. A number is a maximum for lower-is-better metrics; `{max}` or `{min}` say it explicitly. A breach is strictly beyond the limit. Methods are judged one by one and rolled up as worst value and breach count per type, component and container (`rollup`). An unknown value (CRAP without coverage) is never a breach and never zero; it is counted as `unknown`. A bad entry becomes a Problems warning on `designc.json`, never an exception. Findings are warnings only: they show in Problems (click opens file:line in the codebase), as badges at every Code map level and in the type panel. They never reach `Core.gate` and the Python CLI does not know them. `qualityNow()` in `app.js` memoises the judgement on the facts and the `quality` setting.

### Levels, drill-down and adopting components

The Code map has a Context, Containers and Components switcher. Double-clicking a container (or a group at Components level) scopes Components to it, the breadcrumb's All shows every container, and double-clicking empty canvas or pressing Backspace on the map goes up one level. Components is disabled when the as-built model has none (re-extract). Components come from function classes, controllers and endpoint classes, libraries, first folders, and overrides in `designc.json` `extract.components`.

## Known limitations

The DSL parser covers the subset above, not all of Structurizr (no `!include`, dynamic views or archetypes; deployment environments are parsed for display and blast radius only; their relationships and `views { deployment ... }` declarations are read, but there is no layout or drawing of a deployment view beyond the Deployment tab). P models are not run inside the app; only their checks run, as shell commands from decisions. The .NET extractor is regex-based and covers the common registrations listed; other languages are not extracted. The C4 layout is automatic and basic. The built-in agent loop is not MAF: it follows the same contract (role, tools, policy, ledger) so it can later be pointed at a MAF host. `integrations/DesigncTelemetry.cs` is an uncompiled sketch. ACP support targets protocol v1. It has been tested against the mock agent and, on 2026-10-02, against the real `@agentclientprotocol/claude-agent-acp` 0.85.1 (initialize, session/new and a prompt all work through the filtered child environment, using the Claude Code login in `~/.claude`). Codex, Gemini and Copilot adapters are not tested. Agents that authenticate through an environment variable need it listed in the preset's `inherit` or in `designc.json` `acpAgents.<key>.inherit`; `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` are listed for Claude, and Bedrock or Vertex credentials are not. AG-UI support has been tested against `dev/mock-agui-server.js`, not yet against a real MAF host; `integrations/maf-agui-host/` is uncompiled. Installers are unsigned.

Adopted in-process component rels count as DC003 sync hops (only ancestor/descendant pairs are exempt), so a long in-process chain can raise a DC003 warning. DC003 condenses strongly connected components: a sync cycle of at least `chainHops` elements is one finding, and paths run over the condensed graph (`test/dc003-cycles.test.js`). Adopted async rels get a DC001 warning until a `d.delivery` is declared.

## The Python CLI

`python/designc` is the CI form of the compiler: `cd python && python3 -m designc check <registry> [--json]` (or `pip install ./python`, then `designc check`). It reads the same folder as the app (`designc.json`, `model/`, `decisions/`, `requirements/`, `scenarios/`, `ledger/`) and prints findings and gate clauses. Exit code 0 is ready, 1 not ready, 2 the folder cannot be read.

`designc verify-ledger <registry> [--json]` checks the ledger trail (exit 0 clean, 1 errors, 2 the folder cannot be read) and `designc check` records a `gate` event (see the ledger table). Verify rules, identical in `Ledger.verify` (`renderer/ledger.js`, shown in Improve as "Ledger integrity") and `python/designc/verify.py`: V1 every handover follows a ready `gate` event at its revision (a warning when it predates the first gate event; the `r-` prefix is ignored), V2 no handover is dirty, V3 every technical `decision_promoted` follows a passing `check` (decisions not in the registry, of kind business, or an `accept` with no real check are not judged), V4 every line validates, V5 no repeated `event_id` with different content, V6 open `unapproved_change` events (warning), V7 `handovers/` and `handover` events agree both ways, V8 a `source: pipeline` `eval` event after the latest handover has the same `eval_hash` as the handover froze for that eval (`handoverEvals`, read from `evals:` in `handover.yaml`), V9 `pipeline.jsonl` holds only `Ledger.PIPELINE_KINDS` (the kinds a pipeline writes; other files are not judged). `sample: true` events are skipped. Both read raw `{path, text}` files, so they see invalid lines and repeats that the loaders drop.

`designc record <registry> [--by NAME] [--json]` is the eval harness's one way into the ledger: it reads JSON lines on stdin and appends them through `ledger.append_event`. Only `suite_run`, `grader` and `suite_run_finished` are accepted; the list is fixed in `factory.py`, not read from `designc.json`, so a registry cannot widen what an external process may append. Every line is validated first and a batch is all or nothing (exit 0 recorded, 1 nothing recorded with `line N: ...` on stderr, 2 the folder does not exist). `--by` fills `by` on events that name nobody. It needs no model or settings, so it works on a factory registry. `test/factory-record.test.js` covers it.

`designc work <registry> [--json]` lists the work items in `work/` with their state from the ledger, file problems and clashes with active items (exit 0 clean, 1 a problem, 2 the folder cannot be read). It mirrors `Work.validate`, `states` and `conflicts` word for word (`test/work-parity.test.js`); it does not judge done, which needs git and the app. Work files are not a gate input. It also reports `uncovered` (requirement elements no item covers) as warnings that do not change the exit code. The Work view shows them as "Not covered by any item" with Add to item and New item, and an out-of-scope element on an item has Add to requirement (human only, after a confirmation).

It covers the parser, DC000 to DC009, `d.suppress`, the gate (all clauses, including fingerprints, business evidence, scenarios and the ledger's checks and needs-decisions) and `slug_id`. It does not cover drift, diff, blast radius, handover planning, change impact or the code extractor. Differences to know: the canvas extension rules (`registerRules`) do not exist in the CLI; ledger lines are validated only for the kinds the gate reads (`check`, `fitness`, `needs_decision`, `needs_decision_resolved`); finding order uses an approximation of `localeCompare`. YAML is read with `yes`/`no` as strings, as js-yaml does.

When you change `core.js` behaviour that the CLI covers, change `python/designc` in the same commit and extend `test/designc-cli.test.js`.

## Related systems

designc is one of three systems: Design (the design compiler, this app's Design view), Build (any coding pipeline that consumes handovers and may write the ledger; see `docs/pipeline-contract.md`), and Improve (the evals and improvement loop, this app's Improve view). They were called System 1, 2 and 4; data keeps the short codes, so the Langfuse `system` metadata, the roles' `system` field and ledger events still say `S1` (Design) and `S4` (Improve); a pipeline is not a numbered system, its stage is `pipeline` and its telemetry runs are everything not tagged `S1`/`S4`. Use the names in anything a person reads and the codes only in data. The Python CLI in `python/designc` is the CI form of the same compiler and must stay rule-for-rule compatible with `renderer/core.js` (see "The Python CLI" below).

**Deployment models (slice 10).** `Core.parse` reads `deploymentEnvironment` blocks (nested `deploymentNode` with an optional instance count, `infrastructureNode`, `containerInstance`, `softwareSystemInstance`) into `model.deployment = {environments[]}`. They are never added to `elements`, so lint, drift and fingerprints are unaffected. Relationships between deployment elements (`a -> b "desc" "tech"`, or `-> b` inside a node body) resolve against the identifiers declared in the same environment into `env.rels` (`{src, dst, description, technology, line}`, `src`/`dst` as `Node/Child` paths); an unknown identifier is an error with a line. `views { deployment <scope> <environment> "key" }` declarations are listed in `model.deployment.views` and must name a declared environment. Both are mirrored in `python/designc/dsl.py`, and the Deployment tab shows a Links table and the declared view keys. A container instance resolves to its element by identifier; an unknown one is an error with a line. A deployment view's scope must be `*` or a declared software system, else an error (mirrored in `dsl.py`); each view carries `system` (an element id). `Core.deploymentChoices(model)` lists the picker entries (declared views as `key · scope · environment`, then `All of <env>`; ids `view:<key>` / `env:<name>`). `Core.deploymentView(model, wanted)` reads `designc.json` `deployment` as a view key first, then an environment name, and returns `{env, view, choices}`. `Core.deploymentScope(model, env, view)` keeps the nodes holding the system's instances (plus ancestors and linked or contained infrastructure), collapses other systems' instances to `shared` counts and filters the Links. `Core.bySystem` / `splitBySystem` group blast-radius results per software system (this view vs other systems). The Deployment activity (`special:deployment`) draws it read-only as nested boxes with a picker shown when there is a declared view or more than one environment; the last pick is kept per registry in renderer `localStorage`. Edit the DSL in the Design view. The tokenizer now emits bare numbers as `id` tokens.

**Blast radius, unavailable mode (slice 11).** `Core.blastRadius(model, 'Azure/Zone A', {mode: 'unavailable', environment})` takes a deployment node path. An element is *lost* when every instance of it in that environment sits under the node; instances elsewhere make it a *survivor* (reduced capacity, still up). Each lost element then spreads as in `misbehaves` and the worst class wins; lost elements are not repeated under down or degraded. Errors: no deployment, unknown environment, unknown node path. The Deployment view shows it when a node header is clicked.

**Quality attribute scenarios and fitness functions (slice 12).** `scenarios/*.yaml` (human-written; no agent role may write there) holds `id, title, attribute, artifact` (an element name), `stimulus, response, measure {metric, op, value, unit}, requirement?, fitness[]`. `Core.scenarioReport({model, scenarios, ledger})` returns per scenario `status` (`resolved` or `unresolved`), `analytic` and `fitness`. Only availability scenarios have an analytic check: the artifact's `d.availability` times that of everything it depends on through declared sync relationships (async and undeclared are left out, as in `blastRadius`); a missing `d.availability` makes it `unknown` and names the element. No new `d.*` property was added. Every other attribute is judged by its fitness function alone: shell commands run through `host.runCheck` ("Run all fitness functions" in the Scenarios section), recorded as `fitness` ledger events (`checks.jsonl`; `scenario, check, outcome, source`, failure needs `exit_code` or `reason`). Gate clauses: unresolved artifact, availability not met, failing fitness, a scenario missing artifact, attribute or measure. Unknown and unchecked never block, as with demand-driven properties.

**Agent evals (slice 15).** `evals/*.yaml` (human-written; no agent role may write there) holds `id, agent, command, results, thresholds[]`, `maxAge?`. A threshold is `<metric> <op> <number>` (`>= <= > < ==`), parsed by `Core.parseThreshold`; `Core.scoreEval(def, results)` judges a results file `{metrics, cases}` and gives `{outcome, metrics, cases, thresholds, reason?}` or `{error}`. `Core.evalHash` is `hash16` of the eval file text with CRLF as LF. `Core.evalReport({model, evals, ledger, now})` returns one row per element declaring `d.agent.autonomy` with a status: `passing`, `failing`, `stale` (the eval file hash, the agent fingerprint or `maxAge` no longer match the latest result), `unchecked` (no result), `missing` (no eval named, or not in `evals/`) or `invalid`. Only results recorded under the current eval file hash count. `approve-writes` and `autonomous` rows that are not passing become gate clauses (`<agent> (<autonomy>) needs a passing eval: <reason>`); `suggest` rows never block and no `warnings[]` was added to the gate: the Evals section and `designc eval` show them. Other clauses: an eval that is invalid, names an agent not in the model, or repeats an id. Runners: the app (`runEval`/`runEvals` in `app.js`: refuses while a buffer is dirty, runs the command through `host.runCheck`, reads `results` with `host.read`, records an `eval` event with `source: local`), `designc eval` (`cli.py`, `source` defaults to `pipeline` in CI) and the pipeline itself. `evals/` is a gate input (definitions only; `evals/results/` never counts as dirty), a handover copies `evals/*.yaml` and records `evals: {id: hash}` in `handover.yaml`. `Ledger.evalTrends` feeds the Improve view. `docs/eval-results.schema.json` and `docs/eval-wiring.md` describe the results file and how to wire a real suite. `test/evals-parity.test.js` keeps `gate.py` equal to `core.js`.

**Timing and retries (slice 16).** Properties `d.timeout` (rel), `d.latency.max`, `d.fanout` (`sequential` | `parallel`) and `d.retry.budget` (element) are in `SPECS` and `PROPS`. DC007 (error) and DC008 (warning) judge sync rels only (`syncCall`: not async, not ancestor/descendant, source not a person). DC007: a rel's `d.timeout` must be at least `worstCase(callee)` = callee `d.latency.max` plus the sum (maximum for `parallel`) of `d.timeout × (1 + d.retry.max)` over the callee's outgoing sync rels; it is judged only on rels that declare `d.timeout`, and missing values give an `unknown` warning naming them. DC008: the product of attempts along a sync chain must not exceed the receiver's `d.retry.budget`, else `retryAmplification` from `designc.json` (default 4, passed as `Core.check(m, {retryAmplification})`, mirrored in `rules.check` and `cli.py`). `Core.timing(m, opts)` and `Core.amplificationFrom(m, id)` feed the C4 sheet's "Badges: timing" mode. Both rules cite a concept note, not an incident. Tests: `test/timing.test.js` plus the parity model in `test/designc-cli.test.js`.

**Cost forecast (slice 17).** `task` events may carry `handover` (the frozen handover id) and `element`; `handover_closed` (`handover`, `outcome`: delivered | abandoned, stream `designc.jsonl`) ends a handover, written by the Build pipeline or the Close buttons in Build. `task` may carry `run`: such a row is a running total, and only the latest per handover, task and run counts as spend (rows without `run` count as written). `Ledger.elementHistory(events, {window})` totals spend (`totalTokens`, `cost` as recorded, reruns and failures included) per element name and handover, last `window` handovers, oldest first. `Ledger.handoverActuals(events, id)` gives `{tokens, cost, tasks, closed, afterClose}`; tasks after the close event count only in `afterClose`. `Core.forecast({before, after, history, minSamples})` is pure (history is passed in as a Map, so Core does not depend on Ledger): changed means added or changed per `diffModels` (which now gives rels an `ends` pair of names) or at either end of a changed rel; only containers and components; median expected, nearest-rank p90 high, `no basis` below `minSamples` (default 3); `before: null` means everything is added. `Core.freezeForecast` makes the block `handoverPlan({forecast})` writes as `forecast:` in `handover.yaml` (the id hash still covers copied content only). `Core.forecastSummary` is the plain-text summary behind "Copy summary". `computeForecast` in `app.js` reads `designc.json` `currency` (default GBP) and `forecast.minSamples`/`window`; the freeze `confirm` shows the forecast and Build's `handoversBlock` compares it with the actual. The forecast is JS-only: Python learns the two schema additions through the generated `ledger_schema.json`, with no `designc forecast` command and no verify-ledger rule. Contract for the pipeline: `docs/cost-forecast-contract.md`. Tests: `test/forecast.test.js`, `test/forecast-ledger.test.js`.

**Agent pattern (slice 18).** `d.agent.pattern` (enum: `single-call`, `prompt-chain`, `routing`, `parallel`, `orchestrator-workers`, `evaluator-optimizer`, `autonomous-loop`) and `d.agent.patternWhy` (string) are canvas vocabulary properties (`renderer/canvas/vocabulary.js`), so they reach completions through `propsList` and the CLI through `python/designc/canvas_specs.json` (regenerate with `node test/helpers/canvas-specs.js --write`). Rule AG011 in `renderer/canvas/agentic-rules.js` (canvas rules are not mirrored in Python) warns when one of the three complex patterns has a blank `patternWhy`, and gives an `unknown` warning when an agent declares `d.agent.autonomy` without a pattern. Every starter template declares a pattern. Tests: `test/pattern.test.js`.

**Utility tree (slice 19).** A scenario may carry `importance` and `difficulty` (`high`, `medium` or `low`). `Core.scenarioReport` rows expose both (`null` when absent or malformed) and `Core.utilityTree(rows)` groups them by attribute, most important then hardest first, unrated last. Ratings only order: the sole gate effect is a malformed value (`<id>: importance must be high, medium or low`), mirrored in `python/designc/gate.py`. The Scenarios section groups by attribute once any scenario is rated and shows `imp`/`diff` tags; the new-scenario template includes both fields. Tests: `test/utility-tree.test.js` and the parity case S-4 in `test/designc-cli.test.js`.

**Decision assumptions (slice 20).** A decision may carry `assumptions: [{text, review_by}]` (`review_by` is `YYYY-MM-DD`; a YAML date reads the same). `Core.gate` judges them on bound decisions only: a malformed entry (no text, bad or missing date, not a list) gives one `<id>: each assumption needs text and a review_by date (YYYY-MM-DD)`, and a `review_by` before today (UTC, from the gate's `now`) gives `<id>: assumption "<text>" was due for review on <date>`. The gate clause kind is `assumption`. Mirrored in `python/designc/gate.py` (`_assumption_clauses`). "Mark reviewed" in the Decisions list (`reviewAssumptions` in `app.js`, human only) asks for the next date and writes `review_by`, `reviewed_by` and `reviewed_at` on the overdue entries; `Policy.writeVerdict` refuses agent writes whose assumptions carry `reviewed_by` or `reviewed_at`. `list_decisions` returns the assumptions and the Analyst role instructions hold a decision review rubric. Tests: `test/assumptions.test.js` and decision D-5 in `test/designc-cli.test.js`.

**Agent topology (slice 21).** `Core.agentTopology(model)` is pure and returns `{nodes, edges, agents, unguarded}`: the agents (the `Agent` tag, or a declared `d.agent.autonomy`) plus every element one non-structural relationship away. Nodes carry `agent`, `pattern`, `autonomy`; edges carry `effect` (`d.tool.effect`), `approval` (`d.approval`), `protocol` and `unguarded` (irreversible without human approval, the same condition as AG002). The Agent topology activity (`special:topology`, `renderTopology` and `topologySidebar` in `app.js`) draws it read-only with the shared `layout`/`drawModel` over a filtered copy of the model, plus a table of the calls; clicking a node opens it in the model. Tests: `test/agent-topology.test.js`.

**Escape origin (slice 33).** `Ledger.escapeMetrics(events, {uiElements, items})` (pure, `test/escape-origin.test.js`) gives escapes by origin, escapes on `UI` elements, done items with no `ui_acceptance_failed` (`uiEscapeRate`, UI escapes per done item; acceptance first pass; the task id is read as the item id) and `unapproved_change` events on `acceptance/` or `tests/acceptance/` paths (tamper attempts). Improve shows an Origin dropdown per escape and the "Escapes by origin" and "UI and acceptance" blocks (`escapeMetricsHtml` in `app.js`). Display only: never a gate input.
